## Highlights

v2.17.0 goes after two places where the card was quietly getting the numbers wrong. A Cover Group tile used to average its members into a single percentage — three covers at 40% and two at 0% became a tidy 24%, a value none of them held — and now draws the actual spread on its rail and states the real range, or the one member parked away from the rest, instead of that mean. The roster behind it used to list one row per cover, so an entry driving three covers filled three identical-looking rows; rows now fold by owning entry, and a new member_names option lets you rename a roster row per dashboard without renaming the entry itself. A day/night shade's two rails, previously indistinguishable from a blind entry with two separate windows attached, now draw with a brace tying them together, and a per-cover button snaps a cover to its own solar target without engaging manual override. Smaller fixes: the integration and device header icons were swapped back to how they should read, the forecast strip's own line no longer hides under the actual-conditions curve, and the Configure button now deep-links straight to this card's entry.

## Added

- **Layered rail stacks now draw a brace tying them together** — a day/night shade's two rails, or a dual-panel cover's sheer and blackout panels, used to render exactly like a blind entry someone had attached two separate windows to: same glyph, same spacing, nothing to tell them apart. `railsAreOneCover()` checks the entry's `cover_type` against `cover_day_night_shade` and `cover_dual_panel` — the only two types the integration binds more than one cover to per opening — and, when it matches and the tile is drawing two or more rails, adds a hairline connecting them. A single rail, a Cover Group, or any other cover type renders exactly as before, and both kinds of stack carry a `role="group"` with an accessible name so the distinction reaches a screen reader too. Refs #267, #268.

- **A snap-to-target button appears on each cover's position row** — clicking the new `mdi:target` icon drives that cover to the target the row is already drawing a marker for, sending `set_axes` with `force: true`. The integration reads that flag as skip manual-override engagement rather than pin-here, so the move lands and the automation pipeline stays in charge to re-decide on its next run, instead of freezing at the value it just picked itself. It only renders when the integration exposes `set_axes` (`hasSetAxes()`): the legacy per-axis service call has no force flag to carry, so on an older integration this button would do the opposite of its label. The column reserves a fixed 22px rather than auto-sizing, so a cover with no target can't hand those pixels to the track and reflow the bar graph; the tilt row mirrors the same spacer to keep both tracks aligned. Refs #267, #268.

- **A new member_names option renames roster rows per dashboard** — the group tile's editor gained a field that lists the current roster and lets you override any row's label, keyed by `rosterRowConfigKey()`, without renaming the underlying config entry everywhere else it's used. Leaving a field blank restores the entry's own title instead of storing an empty string. Refs #267, #268.

## Changed

- **Group rosters fold by owning entry instead of by cover** — the integration's `member_positions` is keyed per cover, so an entry driving three covers used to contribute three roster rows that were three views of the same entry: same title, same badges, same target marker, and only the moving rail told them apart. `buildRoster()` now groups those covers into one row that carries the entry's covers as its rails, the way a cover tile already renders a multi-cover entry elsewhere on the dashboard. Resolution is sticky, so an entry reload that briefly strips its sensor's attributes doesn't collapse the row back into individual covers and tear down every nested tile card in the process. Refs #267, #268.

- **The group tile's rail and state line now show where members actually are, not their average** — the aggregate sensor publishes a mean, and a group with three covers at 40% and two at 0% used to report a tidy 24%, a value none of them holds. `memberSpread()` draws the rail solid out to the least-covered member with a lighter band to the most-covered one, and the state line reports that range — or, when `memberException()` finds a member being held on manual override or unreachable, that instead of the range. Refs #267, #268.

- **The group tile's position rail now commits only on a deliberate drag** — a tap used to write straight through to `setGroupPosition`, so a stray tap while reaching for the tile could flatten every member onto one value and pull all of them off their own solar targets. The gesture now has to cross a 4px threshold before it previews or commits anything at all; short of that, a tap on the rail does nothing. Refs #267, #268.

- **The Configure button deep-links to this card's config entry** — `_openIntegrationPage()` now appends a `#config_entry=` hash carrying this entry's id to the integration page URL. Home Assistant's own page reads that hash to scroll the matching row into view and highlight it, so you land on this entry instead of an unsorted list, with HA's own Configure cog one click away. The entry's options-flow dialog can't be opened directly from a custom card — its element is a lazy import inside HA's own bundle graph — so this hash is the closest a card can get to a direct jump. Falls back to the bare integration-page URL when no entry_id is available.

## Fixed

- **The integration and device header icons were backwards** — the gear opened the device page and the sliders opened the integration page, which read wrong either way: a gear says configure, and configuring is what the integration page does. The two `ha-icon` glyphs are swapped (`mdi:cog` now opens the integration page, `mdi:tune-variant` the device page); button order and handlers are unchanged. Refs #267, #268.

- **The forecast strip stopped hiding its own line under the actual-conditions curve** — SVG paints in document order, and the actual-curve stroke is thicker than the forecast track, so drawing the actual curve last covered the forecast completely wherever the two agreed, which is most of an ordinary day; it read as a missing blue line rather than as two lines matching. The forecast track now draws on top, so agreement shows as a colored core inside a wider casing and divergence still shows two separate lines. Refs #267, #268.

## Compatibility

- Home Assistant 2024.1+ (no change)
- Adaptive Cover Pro integration: v2.22.1+ baseline (unchanged)
- No config migration needed. `member_names` is optional and existing tile configs load unchanged; group rosters that used to list one row per cover now fold by entry automatically, with no config change required.

## Install / Upgrade

Through HACS, update to v2.17.0. A browser restart is not required.

Home Assistant caches Lovelace ES modules aggressively. After updating, bump the `?v=X.Y.Z` query string on your Lovelace resource URL so the browser picks up the new bundle. A hard refresh alone will not do it.
