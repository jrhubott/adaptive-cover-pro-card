## Highlights

v2.16.0 makes a tile that manages more than one cover finally show all of them. A day/night shade's two rail entities, or a bank of three shades on one config entry, now gets one draggable position rail per cover instead of a single bar for whichever cover happened to be first, and two new config options let you point the tile's buttons at a specific cover or axis when there's more than one. Position bars also changed meaning: a full bar now means the cover is blocking the most sun, which is what the sky compass has always drawn. Covers with a battery sensor show it on the tile icon and in the dialog, every status badge now explains itself on hover, and the forecast strip stopped drawing a tilt curve for shades that don't have slats.

## Added

- **One position rail per managed cover** — a tile whose entry manages more than one cover now renders a draggable rail for each of them, stacked in the space a single bar used to occupy, instead of showing only the resolved cover and leaving the rest with no readout at all. Two new config options, `controls_cover` and `controls_axis`, redirect the tile's buttons to a specific cover or axis when an entry manages several; a third, `covers`, filters and reorders which rails render. All three are optional and default to today's behavior. Refs #259, #261.

- **Cover battery on the tile and in the dialog** — `resolveCoverBatteries()` walks the entity registry to find a battery sensor on a cover's own device, or a `battery_level` attribute where the integration exposes one directly, then `lowestBattery()` picks the worst cell across a multi-cover entry. A cover at or below 20% (`LOW_BATTERY_PCT`) gets a red overlay on the tile icon and a red readout in the dialog; a sensor that stops reporting counts as low rather than being silently dropped. A mains-powered cover with no battery sensor shows nothing. Refs #260, #262.

- **Every badge explains itself** — badge labels are abbreviated for width (a manual badge with a countdown drops its "Manual ·" prefix to a bare clock, a custom-position badge with a slot name drops "Custom ·" to a bare slot name), so a hover tooltip now states the full meaning for every badge kind, not just the ones that read as cryptic before. The custom-position tooltip assembles itself from whichever of slot name, percentage, and floor mode apply to that badge. Refs #264, #265.

## Changed

- **Position bars draw coverage, not openness** — a full bar now means the cover is blocking the most sun, rather than that the cover is open. For an awning or an oscillating awning the two are opposites, so those bars now read inverted from how they did in v2.15.0. Polarity comes from the integration's per-axis `open_blocks_sun` flag through a single render-time transform, which settles a long-standing disagreement with the sky compass — the compass has always drawn coverage. Refs #259, #261.

- **Position rails no longer change color with cover state** — a rail's fill used to take the cover's live state color, so on a multi-rail tile the rails disagreed with each other as covers crossed open and closed. Rails now use one constant, `COVER_ACTIVE_COLOR`; only the tile icon still reflects state. Refs #260, #262.

- **Badge and floor-chip colors now follow the active theme** — colors used to be literal hex values tuned against a light background: `custom_position` measured 1.6:1 contrast on Home Assistant's dark theme, well under the 4.5:1 floor the badges are meant to clear. Backgrounds and text now resolve through `color-mix()` against the theme's own `--primary-text-color`, landing at 6.1:1 in the worst case, and follow a custom HA theme instead of guessing from the OS's light/dark preference. Refs #264, #265.

## Fixed

- **Bar-only tile no longer overlaps its name** — a detailed tile with a position bar and no badges used to center its name/state label across both grid rows while the bar hugged the bottom, so the two drew on top of each other. That layout special-case is gone; a bar-only tile now uses the same grid as a badged one, with the label pinned to the top row. Refs #260, #262.

- **Oscillating awnings no longer draw an inverted wedge on the sky compass** — the compass picked its wedge geometry and its "extended" tooltip wording by testing whether the cover type was `cover_awning`, which an oscillating awning isn't, so it drew the wedge backwards. Both now read the same `open_blocks_sun` polarity the bars use, resolved once through `positionAxisFor()`. Refs #259, #261.

- **Forecast strip stopped drawing a tilt line for shades that don't have slats** — a day/night shade publishes a tilt value on every solar forecast sample even though its own discovery marks that axis unsupported. The strip used to decide what to plot by sniffing sample keys, so it drew a slat curve on a shade with no slats; it now plots one track per axis the entry's discovery (`resolveAxes()`) actually reports as supported. Refs #264, #265.

## Compatibility

- Home Assistant 2024.1+ (no change)
- Adaptive Cover Pro integration: v2.22.1+ baseline (unchanged)
- No config migration needed. `covers`, `controls_cover`, and `controls_axis` are optional; existing tile configs load unchanged, every managed cover still renders in the integration's own order, and the buttons keep targeting the resolved cover's position axis.

## Install / Upgrade

Through HACS, update to v2.16.0. A browser restart is not required.

Home Assistant caches Lovelace ES modules aggressively. After updating, bump the `?v=X.Y.Z` query string on your Lovelace resource URL so the browser picks up the new bundle. A hard refresh alone will not do it.
